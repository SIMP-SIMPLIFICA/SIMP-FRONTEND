01

Stack Tecnológica

Uma SPA em React 19 + TypeScript, servida por Vite, sem framework de gerenciamento de estado global — o cache do TanStack Query cumpre esse papel para todo dado de servidor.

O frontend é organizado por domínio de negócio, não por tipo técnico de arquivo: cada módulo (Diárias, Conselhos, Financeiro, Processos Virtuais, Workspaces…) tem sua própria página em src/pages/, seus componentes em src/components/, seu hook de dados em src/hooks/ e seu cliente de API em src/lib/api/. Essa simetria de três pontas por módulo é o padrão que se repete em todo o projeto.

Camadas e responsabilidades
CamadaLocalResponsabilidade
Páginassrc/pages/<módulo>Composição de tela, roteamento de estado local (filtros, modais)
Componentessrc/components/<módulo>UI reutilizável do domínio; components/ui guarda os primitivos (Radix + shadcn)

01.1Estado e dados de servidor

Não há Redux, Zustand ou Context genérico de estado — TanStack React Query é a única fonte de verdade para dado vindo do backend, com queryClient centralizado em src/lib/queryClient.ts (extraído da árvore React de propósito: o interceptador HTTP precisa chamar queryClient.clear() fora de qualquer componente, ao reagir a uma sessão encerrada pelo servidor). Estado de formulário é responsabilidade do React Hook Form, validado com Zod — o mesmo par usado em praticamente todo formulário do sistema, de cadastro de beneficiário a emissão de diária.

01.2Interface e componentes

Os componentes visuais seguem o padrão shadcn/ui: primitivos acessíveis do Radix UI (diálogo, popover, seleção, abas, dropdown…) estilizados com Tailwind CSS e compostos localmente em src/components/ui — não é uma dependência de biblioteca de componentes, é código do próprio repositório, o que permite ajustar cada primitivo às regras de negócio do SIMP sem esperar por um release upstream. Gráficos usam Recharts; quadros arrastáveis (o board de tarefas dos Workspaces) usam dnd-kit; exportação de planilhas usa xlsx; datas passam por date-fns.

01.3Roteamento e build

React Router 7 no modo data router (createBrowserRouter) define toda a árvore de rotas em um único arquivo (src/router.tsx), incluindo os componentes de guarda descritos na seção 2.1 — a proteção de rota é, portanto, declarativa e visível num só lugar, não espalhada em cada página. O bundler é o Vite 7; testes usam Vitest + Testing Library, com suíte própria em src/test.

02

Segurança no Frontend

A interface assume que o backend é a autoridade final — nenhuma checagem do lado do cliente é tratada como controle de acesso real. O que existe aqui é uma segunda barreira, pensada para esconder o que o usuário não pode ver e cortar chamadas que o servidor recusaria de qualquer forma.

02.1RBAC e guardas de rota

O modelo de permissão é o mesmo do backend: cada usuário tem uma ou mais Roles, cada Role carrega uma lista de chaves de permissão no formato domínio:ação (finance:write, protocols:admin, dailyAllowances:issue…). O endpoint /api/v1/auth/me devolve essa lista já achatada dentro de user.roles[].role.permissions, e src/lib/permissions.ts a reduz a um Set<string> consultado por três funções puras: hasPermission, hasAnyPermission e hasAllPermissions.

O roteador aplica essa checagem em duas camadas independentes, empilhadas por rota:

  • Módulo (ModuleGate) — confere se a organização tem aquele módulo habilitado (user.enabledModules, um feature flag por tenant/plano). Super Admin sempre passa.
  • Permissão (PermissionGate) — confere se o usuário tem ao menos uma das permissões exigidas por aquela tela (anyOf={[...]}).

As duas existem porque resolvem problemas diferentes: uma organização no plano básico pode não ter o módulo de Convênios habilitado (isso é comercial, não é sobre quem é o usuário); dentro de uma organização que tem o módulo, nem todo usuário pode escrever nele (isso é sobre o cargo da pessoa). Tirar qualquer uma das duas reabriria uma tela por digitação direta da URL, mesmo com o item já oculto do menu lateral.

Hoje, qualquer usuário de uma organização com o módulo habilitado acessa a tela — o controle fino por permissão ficou pendente de implementação, não é uma omissão deste resumo.

02.2Gerenciamento de tokens

A estratégia de armazenamento (documentada literalmente no topo de src/lib/auth.ts) segue a prática recomendada contra roubo de token via XSS:

Onde cada token vive
TokenOnde ficaPor quê
access token Variável em memória (módulo JS), nunca em localStorage/sessionStorage Some ao fechar a aba; inacessível a um script injetado que leia o storage do navegador
refresh token Cookie httpOnly, gerido só pelo backend JavaScript não consegue lê-lo nem exfiltrá-lo — o navegador o envia sozinho com credentials: "include"
refresh de impersonation Também em memória (variável separada) Ver seção 2.4 — não pode reaproveitar o cookie do Super Admin

A sessão persiste entre recarregamentos de página sem nada em storage do lado do cliente: ao abrir o app, useAuth chama /auth/me sem token; o interceptador (seção 2.3) recebe o 401 esperado e usa o cookie httpOnly para buscar um access token novo antes de repetir a chamada — o usuário nunca vê essa renovação acontecer.

02.3Interceptador HTTP

Toda chamada ao backend passa por uma única função, apiRequest() em src/lib/api.ts, que funciona como interceptador central. Além de anexar o Authorization: Bearer, ela reconhece três respostas de erro com significado especial e reage antes de qualquer código de tela ver o erro:

Códigos de resposta com tratamento dedicado
RespostaGatilhoAção do interceptador
401 genérico Access token expirado Enfileira chamadas concorrentes, renova via /auth/refresh-token, repete a chamada original
403 ORGANIZATION_SUSPENDED Organização suspensa (inadimplência, bloqueio administrativo) Vai direto para logout — renovar o token não resolveria; limpa o cache do Query e redireciona a /acesso-suspenso
401 SESSION_INVALIDATED Fingerprint de sessão não confere (token em uso de outro dispositivo) Também pula o fluxo de renovação — um token novo carregaria o mesmo problema — e vai direto para /login

O ponto de desenho relevante: nem todo 401/403 é tratado igual. Um 403 comum de permissão nunca desloga ninguém — só os dois códigos específicos acima acionam a saída forçada, checados pelo corpo da resposta, não pelo HTTP status isolado. Chamadas concorrentes durante uma renovação são enfileiradas (failedQueue) em vez de disparar múltiplos refreshes em paralelo — evita a corrida de duas renovações tentando invalidar o mesmo refresh token.

02.4Fluxo de impersonation (Super Admin)

O Painel do Super Admin tem um botão “Entrar” por organização, que assume a sessão de um administrador local sem conhecer sua senha — recurso de suporte, não de vigilância disfarçada: o backend só concede esse token a quem já tem isSuperAdmin.

  1. Super Admin clica “Entrar”; o frontend chama POST /admin/organizations/:id/impersonate.
  2. O access token atual do Super Admin é guardado em sessionStorage (só o access token — o refresh token dele nunca sai do cookie httpOnly, e o endpoint de impersonate não o toca).
  3. O par de tokens da organização impersonada é gravado em memória: o access token substitui o do Super Admin nas próximas chamadas; o refresh token vai para a variável separada _impersonateRefreshToken.
  4. O cache do TanStack Query é limpo por inteiro — nenhum dado da sessão anterior sobrevive à troca de identidade.

A parte mais delicada é a renovação de token durante a impersonação: se o interceptador usasse o caminho normal (cookie + credentials:"include"), o navegador enviaria o cookie httpOnly do Super Admin — que pertence a outra sessão. Por isso, enquanto _impersonateRefreshToken existir, a renovação muda de estratégia: o refresh token vai explicitamente no corpo da requisição, com credentials:"omit", para que o cookie do Super Admin nunca seja lido nem sobrescrito. Sair da impersonação (exitImpersonation) restaura o access token guardado, descarta o token impersonado e limpa o cache — o refresh token original do Super Admin continua válido, porque jamais foi tocado.

02.5Tratamento de erros

Aqui vale uma distinção honesta entre duas coisas que costumam ser confundidas sob o mesmo nome:

  • Erros de rede/sessão têm tratamento global de verdade — é todo o mecanismo da seção 2.3: um único ponto de interceptação, reconhecimento de códigos de negócio, fila de requisições concorrentes e desvio automático de rota.
  • Erros de renderização React (uma exceção lançada durante o render de um componente) não têm um Error Boundary no código hoje — não há componentDidCatch, nenhuma biblioteca como react-error-boundary, e o roteador não define errorElement em nenhuma rota. Um erro de render hoje resulta na tela em branco padrão do React, não numa página de fallback controlada.
Gap identificado

Recomenda-se adicionar um Error Boundary de nível de aplicação (envolvendo <RouterProvider> em main.tsx, ou via errorElement por rota em router.tsx) antes de qualquer demonstração ou uso em produção — hoje a única rede de segurança é o desenvolvedor não deixar o componente lançar.

Erros de requisição individuais (uma mutação que falha, um formulário que o backend rejeita) são, em geral, tratados localmente: cada hook/página captura o erro lançado por apiRequest e o mostra via Toaster (Radix Toast, src/components/ui/toaster) — não existe um handler global de erro de mutação configurado no QueryClient hoje.

Duas camadas adicionais valem menção por completar o quadro de segurança do lado do cliente, mesmo fora do escopo estrito de RBAC/sessão: formulários públicos (recuperação de senha, portal do cidadão) usam Cloudflare Turnstile para prova de humanidade e um campo-isca (honeypot, src/lib/honeypot.ts) com nome deliberadamente plausível para enganar preenchimento automático de bots — o mesmo nome de campo precisa bater com HONEYPOT_FIELD no middleware do backend. E toda sessão autenticada tem expiração por inatividade (useIdleTimer): 30 minutos sem interação encerram a sessão, com aviso nos últimos 60 segundos.

03

Relação com o Backend

Integração via REST puro sobre fetch, sem SDK gerado nem GraphQL — e uma regra simples que atravessa todo o desenho: o tenant nunca é uma decisão do cliente.

03.1Modelo de integração

Não há axios, cliente gerado a partir de OpenAPI, nem camada GraphQL — todas as ~18 áreas de negócio em src/lib/api/ (diárias, conselhos, convênios, processos virtuais, financeiro…) são módulos TypeScript finos que chamam api.get/post/put/patch/delete, o adaptador que embrulha apiRequest() num formato { data } compatível com o que os hooks esperam. Cada arquivo de API tipa manualmente a forma da resposta do backend (não há geração automática de tipos a partir do Prisma/Zod do lado do servidor) — a fonte da verdade dos tipos é mantida por convenção entre os dois times, não por ferramenta.

O backend serve como API-first puro: todas as rotas vivem sob /api/v1/*, autenticação é JWT + cookie (não sessão de servidor), e a própria tela de emissão de documentos (diárias, protocolos) é um bom exemplo do contrato: o frontend nunca calcula hash SHA-256 nem monta o PDF — ele envia a intenção (“emitir”), e o backend devolve o documento já assinado. A UI apenas reflete o estado (PENDING → ISSUED/EMITIDO) e bloqueia edição de campos imutáveis depois da emissão, mas a regra de negócio mora inteiramente no servidor.

03.2Arquitetura multi-tenant nas requisições

Um ponto de desenho notável: o frontend nunca envia um organizationId em header, query string ou corpo de requisição — não existe esse conceito em apiRequest(). O isolamento entre prefeituras/câmaras acontece inteiramente do lado do servidor, a partir do organizationId embutido nas claims do próprio JWT que o usuário carrega. Isso fecha, por construção, uma classe inteira de bug: não existe um parâmetro de tenant que um componente possa esquecer de passar, trocar ou um usuário mal-intencionado manipular via DevTools — o servidor nunca confia em nada que o cliente diga sobre qual organização, só em quem o token prova que ele é.

Do lado da interface, isso aparece como um dado lido, nunca escrito: /auth/me devolve organizationId, enabledModules e a organização completa (nome, plano, CNPJ), e o app usa esses campos só para decidir o que mostrar (seção 2.1) — nunca para compor uma chamada. A única exceção deliberada ao modelo é o Super Admin: isSuperAdmin e o fluxo de impersonation (seção 2.4) existem exatamente para que a pessoa certa possa cruzar essa fronteira, sempre trocando de token — nunca anexando um segundo identificador de organização à mesma sessão.

03.3Separação de responsabilidades

Quem decide o quê
ResponsabilidadeFrontendBackend

O fio condutor é o mesmo em toda a tabela: o frontend otimiza a experiência de operar dentro das regras (esconder o que não interessa, validar cedo, reagir a sessão expirada sem fricção), e o backend continua sendo a única autoridade sobre se uma ação é, de fato, permitida. Essa separação é o que torna o RBAC descrito na seção 2 seguro para depender de configuração de rota em vez de lógica espalhada: mesmo que uma guarda tenha um gap (o caso de Conselhos, seção 2.1), o pior cenário é um usuário ver uma tela — não um usuário conseguir gravar um dado que a API vai recusar de qualquer forma.
